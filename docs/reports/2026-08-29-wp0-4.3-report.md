## Part 1 — `BufferToken` carries the plane layout

### Built

- `BufferToken` gains `stride: u32` and `offset: u32`, taken verbatim from the app's `params.add`.
- C records both per params object and puts them on the forwarded token.
- C **refuses** multi-plane buffers: a second `add`, or one whose `plane_idx` is not `0`, poisons the
  params object so `create_immed` forwards nothing. The log names which of the two refusals happened
  ("no tracked resource" vs "multi-plane"), because they call for different investigations.
- `plane_idx` is **not** carried, per the brief's decision 3.

### Verified — and by what evidence

| Claim | Evidence |
|---|---|
| The token carries the app's real stride and offset | `wayland_proxy_buffer_token.rs::create_immed_emits_a_correct_buffer_token_and_never_asserts` asserts `token.stride == 320` where `width × 4 == 256`, and `token.offset == 4096` |
| A non-zero `plane_idx` refuses the buffer | `a_non_zero_plane_index_refuses_the_buffer` asserts **no** token is forwarded, and that the refusal is not a protocol error |

| The tests actually bite | **Three mutations, three correctly-targeted failures.** `stride: width * 4, offset: 0` fails the token test on the stride assertion **and nothing else**; replacing the poison condition with `if false` fails **both** refusal tests **and neither other test**. Restored: all four pass |
| Nothing else regressed | `cargo test -p rayland-relay -p rayland-c` all green; pure set still **83**; `cargo build --workspace` clean |

The old fixture drove `stride = width × 4` and `offset = 0`, so it would have passed against exactly

## Part 2 — token → `wl_buffer` on S

### Built

- `ExportedFdSource` trait + an `ApplierFdSource` newtype over the `Arc<Mutex<Applier>>` in `main.rs`.
- The dmabuf global's S-side `ObjectId` and bound version recorded in `handle_bind`.
- `plan_buffer_requests` — a **pure** function laying out the three requests.
- `WaylandReplay::synthesize_buffer` — the sending half, routed **before** the sender lookup.
- `scripts/wp0-vkcube-two-machine.sh`.

### The two plan gaps, which are the substance of this report

**Gap 1 — the plan is short by a whole request.** The brief had already caught this and it is
confirmed: C intercepts `create_params` and never forwards it, so on a `create_immed` S has no params
object and the app-side params id is unmapped. A faithful implementation of the *older* plan is
refused at the sender lookup before it ever sees the token. Hence the token check moved ahead of that
lookup, and S originates all three requests.

**Gap 2 — new, and it killed the first run in about four seconds.** The plan (and my code, and my
first test) specified `create_immed`'s child as `wl_buffer` **v1**. It must be the **params object's**
version:

```
thread 'main' panicked: Error when sending request
zwp_linux_buffer_params_v1@9.create_immed: expected version 3 but got 1
```

A Wayland object inherits the version of the object that created it, and `wayland-backend` enforces
it at `rs/client_impl/mod.rs:367` — `child_spec`'s version must equal the **sender's**. `wl_buffer`
has only ever *had* version 1, which is what makes this counter-intuitive: the version is a statement
about lineage, not capability. **My unit test asserted `version == 1` and passed**, because test and
code came from the same wrong belief. Only the compositor knew. The test now asserts the inheritance.

**A robustness defect this exposed, worth carrying into future tasks:** the synthesis path had **no
`catch_unwind`**, which the generic replay path has precisely because `send_request` *panics* rather
than erring on a protocol violation. So a bad Wayland request took down the daemon's **main thread**
and the whole ring session with it. All three sends are wrapped now. Rule: any new `send_request`
call site in this module needs that wrapper.

### Answer to the brief's explicit question about fd ownership

**`send_request` does NOT take ownership and does NOT close the fd.** This tree uses the **pure-Rust**
backend, not the libwayland one — `wayland-client`'s `dlopen` feature forwards only to
`wayland-sys/dlopen` and does **not** enable `client_system`, and `cargo tree` confirms only
`wayland-backend`'s default features. In that backend, `rs/wire.rs:125` handles `Argument::Fd(fd)` by
`BorrowedFd::borrow_raw(fd).try_clone_to_owned()` and pushing the **duplicate** into the socket's
owned out-fd list. So the caller keeps ownership and must let its own `OwnedFd` drop, or leak one per
frame. `synthesize_buffer` holds the `OwnedFd` across all three sends and drops it at the end.

**On the two machines — `scripts/wp0-vkcube-two-machine.sh`, apollo → dop561:**

> **Criterion 4 PASSED. On ONE run. One run is one run, not a rate.**

- **4 of 4** swapchain images became real `wl_buffer`s from relayed tokens: 500×500, XRGB8888,
  LINEAR, `offset 0 stride 2000`.

**Why the silent acceptance is stronger evidence than it looks:** `create_immed` is the *immediate*
variant, which raises a **fatal protocol error** if the buffer is bad. A compositor that takes it
without complaint has actually imported the dma-buf.

### Criterion 5 (4.5) — NOT reached, and here is exactly where it stops

vkcube presents **one** frame and then stalls, **alive**:

- 1 attach, 2 commits, 1 frame-callback request, then nothing.
- Main thread waits on a futex held by Venus's own **`vn_wsi[0,0]`** thread, which sits in `poll`.
- 12 events were delivered back to the app.

**What it is not** — each ruled out, not assumed:

- **Not the token path.** The buffers exist and the compositor accepted them.
- **Not an S-side replay error.** There are none in the log.
- **Not the missing commit gate.** That would tear or present early, not go silent.
- **Not a broken return path for the objects I created.** `IdMaps::insert` populates both directions,
  so a `wl_buffer.release` on a synthesized buffer would translate and be emitted.

So it is waiting for presentation feedback of some kind and **which event is the open question**. This
is the fourth successive case of WP0's written plan being short of what the code needs, and it is a
new investigation rather than something to force inside this brief's scope. I have not chased it.

I could not screenshot to check for a visible window: dop561 runs COSMIC, and `grim` reports

the only way to settle whether anything is drawn.
